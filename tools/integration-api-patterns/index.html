Integration & API Patterns

Integration is chosen by habit more than by design, and the habit is usually whatever the last project did. This page is a selection guide first and a catalog second: three questions that narrow the field, then the patterns with the rule that keeps each one from decaying, then the combinations that work, then the small set of rules worth enforcing across teams.

Pattern names are stable; product names are not. Where a cloud provider's messaging, streaming, or gateway service is needed, use the Cloud Service Mapper to find the equivalent across AWS, Azure, GCP, and OCI.
Framework

Three questions before any pattern

Integration patterns are chosen by habit: whatever the last project used, or whatever the vendor's platform makes easy. Three questions, answered honestly, narrow the field to one or two patterns almost every time.

Synchronous patterns

Use when the caller needs the answer to proceed. The cost is coupling to the callee's availability and latency; the benefit is simplicity and immediate consistency.

Asynchronous patterns

Use when the caller does not need the answer now, when the other side may be down, or when many consumers should react to one fact. The cost is eventual consistency and harder debugging; the benefit is resilience and decoupling.

PatternUse it forDo not use it forThe rule that keeps it healthy
Message queue (point-to-point)Work that must be done exactly once by one consumer: order fulfillment, email sending, background jobsBroadcasting a fact to many consumersDead-letter queue with an owner and an alert; idempotent consumers, because at-least-once delivery is the reality
Publish and subscribeOne fact, many independent reactions, consumers added without touching the producerRequest-reply disguised as events, where the producer secretly waits for a specific subscriberThe producer never knows or cares who listens; if it does, the pattern is wrong
Event streaming (log)High-volume ordered event history, replayable by new consumers, the backbone of event-driven architectureSimple job queues where a stream's operational cost is unjustifiedSchema registry with compatibility rules enforced at publish time; retention decided by the business need to replay, not by default
Change data captureGetting data out of a database into analytics, search, or another system without touching the applicationA substitute for a domain event, because a row change is not a business factTreat the captured change as an internal feed; translate to a domain event before other teams consume it
Saga (choreography or orchestration)A business transaction spanning several services where a distributed transaction is not availableAnything that could be a single service with a local transactionEvery step has a compensating action written and tested before the saga goes live
OutboxPublishing an event reliably in the same transaction as the database writeNothing; it is the correct way to do this and the alternative is lost eventsThe relay that reads the outbox is monitored for lag like any other consumer

Data integration patterns

Moving data in bulk is not an integration problem to solve with APIs. Most systems that try end up with a nightly job that calls an endpoint a million times.

PatternUse it forTrade-off
Scheduled batch, file or bulk exportLarge periodic movements between systems that tolerate hours of latency: finance close, regulatory extracts, partner feedsSimple and cheap; latency and the operational fragility of schedules and file formats
ELT into a warehouse or lakehouseAnalytics, reporting, and anything that needs a joined view across many sourcesDecouples producers from consumers entirely; the platform becomes a dependency and the data has an owner problem, covered in Data Strategy

Reference

Common combinations that work

Real architectures combine patterns. These are the combinations that recur in healthy estates.

  1. Command in, events outA service accepts synchronous commands over REST or gRPC, writes to its own database, and publishes domain events through an outbox. Consumers subscribe. The service never calls other services synchronously to complete a write.
  2. Gateway plus BFF plus internal gRPCPublic traffic enters through a gateway that handles auth and rate limits, hits a client-specific BFF, which calls internal services over gRPC. Nothing internal is reachable from outside.
  3. Event stream plus CDC plus lakehouseOperational events flow through a stream; CDC captures the database changes that predate the event design; both land in the lakehouse for analytics. The lakehouse never feeds an operational decision back synchronously.
  4. Queue plus saga for long-running business processesAn order, a claim, a loan application: a saga orchestrator steps through services via queues, each step idempotent, each with a compensating action, with the state of every in-flight process visible in one place.
  5. Strangler with an anti-corruption layerNew services sit behind the same gateway as the legacy system; an anti-corruption layer translates between the legacy model and the new domain model so the new services never inherit the old shape. See Legacy Modernization Execution.
Governance

The rules an architecture review should enforce

Pattern choice is a team decision. These rules are the small set an Architecture Review Board should hold across teams, because violating them is expensive for everyone else.

  • Every published contract (OpenAPI, proto, event schema) is versioned, in a repository, reviewed, and never broken in place
  • No service reads another service's database; the only path is the contract
  • Every asynchronous consumer is idempotent and has a dead-letter path with an owner
  • Every synchronous call across a network boundary has a timeout, a retry policy with backoff, and a circuit breaker
  • Every integration is observable end to end: a correlation identifier propagates through calls and messages, and a trace exists for a single business transaction
  • Domain events describe business facts in business language, not table changes
  • Internal integration does not go through a vendor iPaaS unless the vendor owns both ends; iPaaS is for SaaS-to-SaaS
  • Any integration that runs on a schedule has an alert when it does not run, not only when it fails
Common pitfall

The enterprise service bus reborn as a platform

Every decade the same mistake arrives under a new name: a central integration team owning a central integration product through which everything must pass.

What it looks like

The integration team owns the bus, the iPaaS, or the event platform, and every new integration is a ticket to that team. Transformations accumulate inside the product where no product team can see them. The team becomes the bottleneck for every delivery, the product becomes the system nobody dares upgrade, and the business logic that leaked into it is the next modernization project.

The counter-move

A central team owns the platform (the broker, the gateway, the schema registry, the observability) and the rules above. Product teams own their contracts, their consumers, their transformations, and their on-call. The platform team's success metric is how little any team needs to talk to them.
