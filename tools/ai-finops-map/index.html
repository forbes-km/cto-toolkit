AI FinOps Map

Cost modeling across the same Azure-managed and self-hosted split as the Architecture Map, since the cost shape of a system follows directly from how it's built.

Cost modeling here is directional, not a substitute for building your own model with your actual volume, region, and negotiated pricing. Vendor pricing changes frequently; verify current rates before using specific numbers in a budget decision.
1

Pricing model: tokens vs amortized hardware

The fundamental cost shape differs before any workload-specific decisions get made.

Azure-managed

Pay-as-you-go is billed per token, input and output priced separately, output typically several times more expensive than input. Cost scales directly and immediately with usage, visible per-call, but unpredictable at the account level until volume stabilizes.

Self-hosted / open-weight

Cost is amortized GPU time (purchase or lease depreciation, power, cooling, ops staff), largely fixed regardless of query volume until you hit a capacity ceiling and need to add hardware. Marginal cost per additional query approaches zero until that ceiling, then jumps in a large step when you provision another node.

The break-even point is a real number, not a vibe. Calculate it: (fixed self-hosted cost per month) divided by (per-token Azure cost) gives the query volume where self-hosting starts winning. Below that volume, pay-as-you-go almost always wins on total cost.
2

Reserved capacity vs GPU procurement

Committing ahead of time to guarantee throughput and control cost variance.

Azure-managed

Provisioned Throughput Units (PTU) reserve dedicated capacity at a flat monthly rate, converting variable token cost into a predictable fixed cost, but only pays off above a specific utilization threshold; idle PTU capacity is money spent on nothing.

Self-hosted / open-weight

Owning or leasing GPUs is the hardware equivalent of a PTU reservation: a large fixed commitment that only pays off at sustained utilization. Renting from a GPU cloud (on-demand) is the hardware equivalent of pay-as-you-go, more expensive per hour but no idle-capacity risk.

3

Chargeback & unit economics

Making AI spend attributable to the team or product that generated it, not a single opaque line item.

Azure-managed

Cost Management's tagging and scope hierarchy lets you attribute Foundry deployment spend to a subscription, resource group, or tag, feeding a per-team or per-product chargeback model the same way any other Azure resource would.

Self-hosted / open-weight

No managed billing hierarchy to lean on; attribution requires your own request-tagging at the application layer (which team or product initiated the call) correlated against GPU-hour cost allocated proportionally to usage. This is meaningfully more engineering work to build.

The metric that actually matters in both environments is cost per unit of business value, cost per resolved support ticket, cost per underwriting decision, not cost per token or cost per GPU-hour. Build the unit economics dashboard around the business metric first and let infrastructure cost roll up into it.
4

Cost observability & budget alerting

Catching a cost anomaly (a runaway agent loop, a misconfigured retry, a prompt that ballooned in size) before the monthly bill does.

Azure-managed

Azure Cost Management budgets with action-group-triggered alerts at defined thresholds; Azure Monitor can alert on token consumption rate directly if instrumented, catching an anomaly within the billing period rather than after it closes.

Self-hosted / open-weight

No native billing-anomaly alerting since there's no per-token bill to watch. The equivalent signal is GPU utilization and request-rate anomalies via Prometheus alerting, an unusual spike in request volume or output length is the leading indicator you actually have.

5

Model selection as a cost lever

The single highest-leverage FinOps decision, made once per use case, before any of the above matters.

Azure-managed

Foundry's model catalog spans a wide price-performance range; routing simple classification or extraction tasks to a smaller, cheaper model and reserving the frontier model for genuinely complex reasoning is often a larger cost lever than any PTU or reservation optimization.

Self-hosted / open-weight

Same principle, and arguably higher stakes: a smaller open-weight model (7B to 14B class) served efficiently can handle a large share of production traffic at a fraction of the GPU footprint a frontier-class open-weight model requires, if the task doesn't actually need frontier reasoning.

This is the FinOps decision most teams skip because it requires an evaluation harness to prove the cheaper model is good enough, and building that harness feels like overhead. It almost always pays for itself faster than infrastructure optimization does.
6

Waste: idle reservations and orphaned capacity

The unglamorous but highest-frequency cost leak in both environments.

Azure-managed

PTU reservations sized for peak load sitting idle most of the day; forgotten dev/test Foundry deployments left running after the project using them ended. Both invisible unless someone is specifically auditing deployed resources against actual active use cases.

Self-hosted / open-weight

GPU nodes provisioned for a launch that never reached expected volume, or a dev cluster left running after the project wound down. Same failure mode, higher absolute cost per incident since GPU hardware commitments are larger and stickier than a cloud service you can just delete.

Run a quarterly audit matching every deployed model endpoint or reserved GPU allocation against an active, named use case. Anything without one gets decommissioned, not just flagged.
Reference only. Pricing, reservation models, and hardware costs change quickly; verify current numbers against primary sources before relying on this for a budget or investment decision.
