1

Pricing model: tokens vs amortized hardware

The fundamental cost shape differs before any workload-specific decisions get made.

AWS

Bedrock is billed per token, input and output priced separately, output typically several times more expensive than input, with per-model rates ranging from a few cents per million input tokens for the smallest models to several dollars for frontier models, a spread of more than a hundredfold.[2] Cost scales directly and immediately with usage, unpredictable at the account level until volume stabilizes.

Azure

Pay-as-you-go is billed per token, input and output priced separately, output typically several times more expensive than input. Cost scales directly and immediately with usage, visible per-call, but unpredictable at the account level until volume stabilizes.

GCP

Vertex AI bills current Gemini models per token, input and output metered separately; older model generations were metered per character, so check which meter applies to the model you pick. An easy-to-miss cost multiplier: Gemini's internal reasoning (thinking) tokens are billed as output, and on reasoning-heavy requests they can inflate cost several times beyond what the visible response length suggests.

OCI

On-demand OCI Generative AI is billed per transaction (character-based) for on-demand inference, separate from the per-unit-hour rate that applies once you move to a dedicated cluster. Consumption draws against an existing Universal Credits commitment rather than a standalone bill.

Self-hosted / open-weight

Cost is amortized GPU time (purchase or lease depreciation, power, cooling, ops staff), largely fixed regardless of query volume until you hit a capacity ceiling and need to add hardware. Marginal cost per additional query approaches zero until that ceiling, then jumps in a large step when you provision another node.

The break-even point is a number you can calculate, so calculate it: (fixed self-hosted cost per month) divided by (per-query managed cost) gives the query volume where self-hosting starts winning. Below that volume, pay-as-you-go almost always wins on total cost.
Sources
  1. AWS, Amazon Bedrock pricing

Reserved capacity vs GPU procurement

Committing ahead of time to guarantee throughput and control cost variance.

AWS

Provisioned Throughput reserves dedicated capacity in model units, billed hourly whether used or not, with no-commitment, 1-month, and 6-month terms.[2] Only pays off above sustained utilization; buying a 6-month commitment before traffic is stable is the single fastest way to overspend here. Some custom and fine-tuned models still require Provisioned Throughput rather than on-demand billing; check the deployment options for the specific model before assuming pay-as-you-go is available.

Azure

Provisioned Throughput Units (PTU) reserve dedicated capacity at a flat monthly rate, converting variable token cost into a predictable fixed cost, but only pays off above a specific utilization threshold; idle PTU capacity is money spent on nothing.

GCP

Provisioned throughput, priced per PTU per hour rather than per token, with Azure Reservations for 1-month or 1-year terms at a discount that varies by model family and term. Hourly billing suits short or variable use; for sustained production volume a reservation is usually cheaper. Compare against the pay-as-you-go bill at your actual volume before reserving.[3]

OCI

Dedicated AI clusters bill per unit-hour, but the distinctive gotcha here is the minimum commitment: hosting clusters require at least 744 unit-hours, roughly a full month, even if actual usage is far lower. That minimum doesn't exist on the other three clouds' reserved-capacity tiers.

Self-hosted / open-weight

Owning or leasing GPUs is the hardware equivalent of a reserved-capacity commitment: a large fixed cost that only pays off at sustained utilization. Renting from a GPU cloud (on-demand) is the hardware equivalent of pay-as-you-go, more expensive per hour but no idle-capacity risk.

Sources
  1. AWS, Amazon Bedrock pricing
  2. Microsoft Learn, provisioned throughput billing and cost management
3

Chargeback & unit economics

Making AI spend attributable to the team or product that generated it instead of leaving it as one opaque line item.

AWS

Cost Explorer's tagging and cost allocation tags attribute Bedrock spend to a team, product, or environment tag, feeding a per-team chargeback model the same way any other AWS resource would.

Azure

Cost Management's tagging and scope hierarchy lets you attribute Foundry deployment spend to a subscription, resource group, or tag, feeding a per-team or per-product chargeback model the same way any other Azure resource would.

GCP

Cloud Billing labels plus BigQuery billing export let you attribute Vertex AI spend down to the label or project level, queryable alongside the rest of the GCP bill rather than as an isolated line item.

OCI

Compartment structure plus tag-based attribution in OCI Cost Analysis, with FOCUS-format billing exports increasingly the default pipeline for feeding a chargeback model. Cost Analysis falls back to a tagless view when tag coverage is incomplete.

Self-hosted / open-weight

No managed billing hierarchy to lean on; attribution requires your own request-tagging at the application layer (which team or product initiated the call) correlated against GPU-hour cost allocated proportionally to usage. This is meaningfully more engineering work to build.

The metric that matters across every environment is cost per unit of business value: cost per resolved support ticket, cost per underwriting decision. Cost per token and cost per GPU-hour are inputs to that number and poor substitutes for it. Build the unit economics dashboard around the business metric first and let infrastructure cost roll up into it.
4

Cost observability & budget alerting

Catching a cost anomaly (a runaway agent loop, a misconfigured retry, a prompt that ballooned in size) before the monthly bill does.

AWS

AWS Budgets with configurable thresholds and Cost Anomaly Detection using machine learning to flag unusual spend patterns automatically, without a manually defined rule for every scenario.

Azure

Cost Management budgets with action-group-triggered alerts at defined thresholds; Monitor can alert on token consumption rate directly if instrumented, catching an anomaly within the billing period rather than after it closes.

GCP

Budgets & Alerts plus Cost Anomaly Detection at the billing-account level; the reasoning-token cost multiplier from Stage 1 is exactly the kind of anomaly this catches before it compounds across a month of traffic.

OCI

OCI Cost Analysis with budget-based alerts, increasingly paired with FOCUS-format billing exports for teams that have moved off the native dashboard onto a broader FinOps pipeline.

Self-hosted / open-weight

No native billing-anomaly alerting since there's no per-token bill to watch. The equivalent signal is GPU utilization and request-rate anomalies via Prometheus alerting. An unusual spike in request volume or output length is the leading indicator you have.

Model selection as a cost lever

The single highest-leverage FinOps decision, made once per use case, before any of the above matters.

AWS

Bedrock's catalog spans a more than hundredfold price range across model tiers;[2] routing simple classification or extraction tasks to a cheaper model (Nova Micro or Haiku-class) and reserving the frontier model for complex reasoning is often a larger lever than any reservation optimization.

Azure

Foundry's model catalog spans a wide price-performance range; routing simple classification or extraction tasks to a smaller, cheaper model and reserving the frontier model for complex reasoning is often a larger cost lever than any PTU or reservation optimization.

GCP

Gemini 2.5 Flash-Lite at $0.10 input and $0.40 output per million tokens on Vertex AI, against $1.25 input for Gemini 2.5 Pro;[4] the same routing principle applies, with the added wrinkle that reasoning tokens make the effective cost gap between tiers larger than the sticker price alone suggests.

OCI

OCI's catalog spans Oracle-curated and partner models (Cohere, Llama, xAI Grok) at meaningfully different price points; the same routing principle applies, and dedicated-cluster pricing tiers differ enough by model family that the choice compounds with the reserved-capacity decision from Stage 2.

Self-hosted / open-weight

Same principle, and arguably higher stakes: a smaller open-weight model (7B to 14B class) served efficiently can handle a large share of production traffic at a fraction of the GPU footprint a frontier-class open-weight model requires, if the task doesn't need frontier reasoning.

This is the FinOps decision most teams skip because it requires an evaluation harness to prove the cheaper model is good enough, and building that harness feels like overhead. It almost always pays for itself faster than infrastructure optimization does.
Sources
  1. AWS, Amazon Bedrock pricing
  2. Google Cloud, Vertex AI generative AI pricing
6

Waste: idle reservations and orphaned capacity

The unglamorous but highest-frequency cost leak across every environment.

AWS

Provisioned Throughput reserved for peak load sitting idle most of the day; forgotten Knowledge Bases vector storage (OpenSearch Serverless bills a minimum of about $350 a month for a standard collection even at zero query traffic; dev-test collections cost about half that, and newer collection types scale to zero when idle)[5] left running after a project ends. Both invisible unless someone is specifically auditing deployed resources against active use cases.

Azure

PTU reservations sized for peak load sitting idle most of the day; forgotten dev/test Foundry deployments left running after the project using them ended. Both invisible unless someone is specifically auditing deployed resources against actual active use cases.

GCP

Online prediction endpoints, Vector Search nodes, and Workbench instances all bill per hour regardless of traffic; a forgotten deployed endpoint is one of the most common GCP AI cost surprises, silently running up thousands a month for zero real usage.

OCI

Idle dedicated AI clusters are described directly in Oracle's own licensing guidance as the top cost trap: a reserved cluster bills around the clock, and under-utilized, can cost many times what on-demand inference would for the same volume, compounded by the 744-hour minimum commitment from Stage 2.

Self-hosted / open-weight

GPU nodes provisioned for a launch that never reached expected volume, or a dev cluster left running after the project wound down. Same failure mode, higher absolute cost per incident since GPU hardware commitments are larger and stickier than a cloud service you can just delete.

Run a quarterly audit matching every deployed model endpoint or reserved capacity allocation, on any provider, against an active, named use case. Anything without one gets decommissioned. Flagging it and moving on is how the next audit finds the same list.
Sources
  1. AWS, Amazon OpenSearch Service pricing

Prompt caching

A cost lever specific to how LLMs are billed, with no equivalent in traditional cloud FinOps.

AWS

Prompt caching on Bedrock caches a stable prefix (system prompt, long reference document) and bills cache reads at 10 percent of the standard input rate for Anthropic models, up to 90 percent savings on context-heavy applications.[2] Same architectural discipline as every provider here: stable content first, dynamic content last, or the cache never hits.

Azure

Prompts of 1,024 tokens or more are cached automatically on supported models, with no opt-in, and cached input tokens are billed at a discount on Standard deployments (up to 100 percent on provisioned deployments). The exact rate depends on the model, so check the pricing page.[6] The architectural work is keeping the cacheable part of the prompt byte-identical and in the same position on every request; dynamic content has to move to the end, after the cacheable prefix, or the cache never hits.

GCP

Context caching bills cached input at a fraction of the normal rate (75 percent off for Gemini 2.5 Flash-Lite at this review) plus a storage charge per million tokens per hour the cache is held. The discount differs by model, so check the pricing page for the model you use.[4]

OCI

As of this review, OCI does not document a general-purpose prompt caching discount comparable to the other three clouds. Treat this lever as unavailable on OCI until Oracle publishes one, and re-check before a renewal.

Self-hosted / open-weight

vLLM and most modern serving stacks support prefix caching (often called automatic prefix caching or APC) natively, and the same discipline applies: stable content first, dynamic content last. The saving shows up as GPU time not spent recomputing the same prefix, rather than a line-item discount on a bill, so it has to be measured through throughput and latency metrics instead of a cost dashboard.

Caching discounts are not permanent. Providers have already changed how cached tokens are priced more than once, so re-verify any specific caching discount against current pricing before it goes into a budget.
Sources
  1. AWS, Amazon Bedrock pricing
  2. Google Cloud, Vertex AI generative AI pricing
  3. Microsoft Learn, prompt caching with Azure OpenAI
8

Batch / asynchronous processing

Trading latency for a flat discount, available whenever the workload can tolerate a delayed result.

AWS

Batch Inference processes a submitted job asynchronously at 50 percent off standard on-demand pricing.[2] Batch doesn't support tool calling, structured output, or multi-turn conversation, so it is a different execution model rather than a slower version of the same one.[7] Don't move an agent loop to Batch because the token price is lower.

Azure

The Batch API processes a submitted job asynchronously, typically within a 24-hour target, at 50 percent less than Global Standard pricing.[8] Useful for nightly document processing, bulk content generation, embeddings refreshes, and model evaluations. Not usable for interactive chat or any customer-facing path expecting an immediate response.

GCP

Gemini batch prediction runs non-urgent jobs asynchronously at 50 percent off standard token rates.[4] One gotcha applies to batch prediction on custom-trained models rather than Gemini: Google bills for the provisioned cluster runtime rather than active processing time, so under-filled jobs cost more per prediction than expected. Batching requests into larger groups is the fix.

OCI

As of this review, OCI does not document an asynchronous batch-discount tier comparable to the other three clouds. Treat this lever as unavailable on OCI until Oracle publishes one, and re-check before a renewal.

Self-hosted / open-weight

The equivalent move is scheduling batch workloads for off-peak GPU capacity, or running them through the same continuous-batching serving stack at a lower priority queue than interactive traffic. There's no separate billed rate to point to. The saving comes from higher GPU utilization on hardware that would otherwise sit idle overnight, which still has to be measured to know it's happening.

The same discipline applies across every environment: anything without a hard latency requirement is a batch candidate. Auditing which workloads still run on the interactive path out of habit is a recurring source of avoidable spend.

What the example leaves out

The model bill is usually not the largest line once a feature is in production.

Costs to add

Retrieval infrastructure and embeddings, evaluation runs, logging and tracing, guardrail calls, human review of the escalated 40 percent, and the engineering time to maintain prompts as models change.

What to report

Cost per resolved outcome next to the cost of the human alternative, and the trend month over month. Flexera's 2026 survey found waste growing on AI workloads even as overall cloud value improved[1], so an unmeasured pilot is where that waste starts.
