AI Architecture Map

Pipeline stage by pipeline stage, from raw documents to a grounded, human-supervised, secured response. A compact reference table below covers six capabilities across all four major clouds at a glance; the stage-by-stage depth that follows uses a toggle, click AWS, Azure, GCP, OCI, or Self-hosted once and every stage on the page switches to that environment's answer. Product names and service naming reflect 2026 offerings; verify current service names against primary sources before relying on any of this for a design decision, this space moves fast.

Not every stage differs by environment. Chunking logic and the MCP protocol layer run in your own application code and are identical everywhere; where that's true, it's called out as a single statement rather than padded into five near-duplicate answers. Human-in-the-loop is a partial case: the tiering logic and failure modes are identical across every environment, but the concrete queue and notification infrastructure differs by provider, so that stage keeps the toggle while its own same-note explains what stays constant.

Stage 1

Document intelligence / ingestion

Turning raw PDFs, scans, forms, and images into machine-readable structured content: OCR, layout analysis, table and key-value extraction.

AWS

Textract for OCR, layout, table, and key-value extraction; pair with Comprehend for downstream entity extraction on the recovered text.

Azure

AI Document Intelligence for OCR, layout, table, and key-value extraction using prebuilt or custom-trained models. AI Content Understanding covers multimodal parsing (image, audio, video) as a Foundry service when documents aren't purely text/table.

GCP

Document AI, with prebuilt processors for common document types (invoices, IDs, contracts) and a general OCR processor for everything else.

OCI

Document Understanding for OCR, table, and key-value extraction through prebuilt AI models, customizable for industry-specific extraction needs.

Self-hosted / open-weight

The unstructured library or docling for parsing, paired with Tesseract or PaddleOCR for text recognition. For layout-aware extraction, a locally served vision-language model (Qwen-VL, InternVL, or a comparable open-weight multimodal model) handles document QA-style extraction where prebuilt OCR alone isn't enough.

Stage 2

Chunking

Splitting extracted content into retrieval-sized units without breaking semantic units apart.

Same across every environment

Chunking is orchestration-layer logic, not a cloud primitive, so this one doesn't change when you switch the toggle above. LangChain's RecursiveCharacterTextSplitter, embedding-similarity-based semantic chunking, or a managed index's built-in chunking step (Azure AI Search's integrated vectorization skillset is one example) all run identically regardless of which provider or self-hosted stack sits downstream. The choice of algorithm matters far more than the choice of cloud.

Stage 3

Embeddings

Converting chunks into vectors for semantic retrieval.

AWS

Titan Text Embeddings via Bedrock, or Cohere Embed for multilingual needs, billed per token with no separate deployment step.

Azure

OpenAI embedding models (text-embedding-3-large/small) via Foundry, pay-as-you-go per token or reserved via provisioned throughput for predictable latency at volume.

GCP

Vertex AI text embedding models, billed per character, with native integration into BigQuery for embedding data already living there.

OCI

OCI Generative AI embedding models, callable through the same API surface as OCI's generation models.

Self-hosted / open-weight

Open-weight embedding models (BGE-large, E5-mistral, Nomic Embed, GTE) served on owned GPUs via Hugging Face Text Embeddings Inference (TEI) or an Infinity server. No per-token bill; cost is amortized GPU time.

Stage 4

Vector indexing & retrieval

Storing embeddings for fast approximate nearest-neighbor search, typically combined with keyword search for hybrid retrieval.

AWS

OpenSearch Service for large-scale ANN search with hybrid BM25 support, or pgvector on RDS/Aurora for teams staying inside an existing Postgres footprint.

Azure

AI Search: HNSW vector index, hybrid (vector + keyword + semantic ranking) query mode, metadata filters, and ACL-aware secure access baked into the index itself.

GCP

Vertex AI Vector Search for dedicated ANN at scale, or vector functions inside BigQuery when the data already lives there and a separate index is overhead.

OCI

AI Vector Search built directly into Oracle Database 23ai, keeping vectors and relational data in one system rather than a separate store.

Self-hosted / open-weight

pgvector if you want to stay inside an existing Postgres footprint, or a dedicated vector database (Qdrant, Weaviate, Milvus) for larger-scale ANN search with metadata filtering. Hybrid search typically pairs the vector store with OpenSearch/Elasticsearch for BM25, or uses a store with native hybrid support.

Stage 5

Reranking & context assembly

Re-scoring initial retrieval results with a more precise (and more expensive) model before assembling the final context window.

AWS

No first-party managed reranker; Cohere Rerank is available as a Bedrock marketplace model, called as an explicit extra step, same pattern as self-hosting one.

Azure

AI Search's semantic ranker applies a Microsoft-trained cross-encoder as an L2 re-ranking pass over the initial hybrid results, exposed as a query-type option, no separate deployment required.

GCP

Vertex AI Search includes a ranking API as part of its managed search stack, applying a similar L2 re-ranking pass over initial results.

OCI

Native Cohere Rerank models (Rerank 3.5, and Rerank 4 as of 2026) built into the Generative AI service itself, called directly via the RerankText API, available both on-demand and through dedicated clusters. Unlike AWS, this is first-party, not a marketplace add-on.

Self-hosted / open-weight

An open cross-encoder reranker (BGE-reranker, Jina Reranker) served alongside the embedding model, typically on the same TEI/Infinity serving stack, called as an explicit extra step in your retrieval code.

Stage 6

Generation / model serving

Running the language model itself against the assembled, grounded context.

AWS

Bedrock model deployment: unified Converse API across Claude, Titan, Llama, and Mistral. Provisioned Throughput for predictable latency at volume, on-demand for variable load, plus a batch tier at a discount for non-interactive workloads.

Azure

AI Foundry model deployment: Azure OpenAI models or the Foundry Model Catalog's open-weight options, on managed online endpoints. Provisioned Throughput Units (PTU) for predictable latency and cost at volume, or pay-as-you-go token billing for variable load.

GCP

Vertex AI model deployment: Gemini-first, with third-party and open-weight models available through Model Garden. Provisioned throughput and pay-as-you-go both available, same shape as the other two.

OCI

OCI Generative AI model deployment, native and third-party models, callable through the same managed endpoint pattern as the rest of the OCI Generative AI service.

Self-hosted / open-weight

vLLM or TGI serving an open-weight model (Llama, Qwen, Mistral, DeepSeek-class) on owned or leased GPUs, with continuous batching and paged KV-cache for throughput. Ollama for smaller-scale or development use; llama.cpp for CPU/edge deployment.

Stage 7

Agent tool layer (MCP)

Giving the model controlled access to enterprise systems and external data through defined tools.

AWS

Bedrock Agents, AgentCore, and Flows for managed tool-use orchestration, or a self-built MCP server fronting enterprise systems, called from a Bedrock-hosted agent.

Azure

AI Foundry Agent Service with built-in tool calling, or a self-built MCP server fronting enterprise systems, called from a Foundry-hosted agent.

GCP

Vertex AI Agent Builder for managed tool orchestration, or a self-built MCP server called from a Vertex AI-hosted agent.

OCI

OCI Generative AI Agents, with tool and API orchestration built into the same service that handles RAG.

Self-hosted / open-weight

Identical MCP server code across every environment; MCP is a transport protocol, not a cloud primitive. The real dependency is whether your serving stack (vLLM, TGI) supports the model's native tool-calling chat template, so verify per model rather than assuming.

The protocol layer is the same everywhere. What changes across all five environments is only whether the serving stack in question has tool-calling support wired up for the specific model you chose.
Stage 8

Human-in-the-loop

Routing outputs by risk and reversibility to a review queue, notification layer, and durable orchestration that can pause and resume a process for hours or days.

AWS

DynamoDB for the review queue/state table, SNS or SQS plus EventBridge for notification and escalation timers, Step Functions for the durable orchestration that survives a pause spanning hours or days.

Azure

Cosmos DB or Azure SQL for the review queue/state table, Teams webhook plus Power Automate for notification and escalation timers, Azure Durable Functions for the durable orchestration that survives a pause spanning hours or days.

GCP

Firestore for the review queue/state table, Pub/Sub for notification, Cloud Workflows for the durable orchestration spanning the pause.

OCI

Autonomous Database for the review queue/state table, Notifications service for alerts, OCI Functions chained via Events for the durable orchestration.

Self-hosted / open-weight

Postgres for the queue, Slack webhook for notification, Temporal (self-hostable) for durable orchestration. Functionally the same architecture as every column above, different concrete products.

This entire stage sits above the model, at the application layer. The tiering logic (reversibility/blast-radius, not confidence alone) and the queue-overload failure mode are identical across all five environments. See the deep HITL reference for the full design detail.
Stage 9 · cross-cutting

Security & threat model

Prompt injection, tool-call authorization, and the model supply chain. This isn't a stage the data passes through once, it applies to every stage above.

AWS

Bedrock Guardrails runs as a pre-processing gate for content filtering and PII redaction on both input and retrieved content. Tool calls run under IAM roles scoped per agent; Bedrock endpoints sit behind VPC endpoints with public access disabled.

Azure

AI Content Safety's prompt shields run as a pre-processing gate on both user input and any retrieved or tool-returned content before it reaches the model, since an injected instruction can arrive through a poisoned document just as easily as through the chat box. Tool calls run under managed identities with least-privilege RBAC scoped per agent through Entra ID. Foundry deployments sit behind private endpoints and VNet integration; AI Search restricted to private link with public network access disabled.

GCP

Two layers: Gemini's built-in Safety Settings for per-request content filtering (hate speech, harassment, sexually explicit, dangerous content, configurable thresholds), plus Model Armor as a separate dedicated service for prompt injection and jailbreak detection, sensitive data protection, and malware scanning. IAM and VPC Service Controls provide the network and identity isolation layer underneath both.

OCI

OCI Guardrails, a named, documented feature with three protections: content moderation (hate speech, harassment, violence, explicit material), prompt injection defense (binary risk scoring on embedded malicious instructions), and PII detection. Configurable in Inform mode (logs and returns results) or Block mode (rejects the request), available on both on-demand and dedicated cluster endpoints.

Self-hosted / open-weight

No managed prompt-shield equivalent. Typically an open guard model (Llama Guard, or a policy layer like NeMo Guardrails) run as a pre and post filter in your own pipeline, tuned and maintained by you. Tool-call authorization is your own implementation at the MCP server layer, commonly OAuth2 or mTLS between the agent runtime and each tool server. Model and weight supply chain matters here specifically: verify checksums and provenance of downloaded weights against the publisher's signed release. Network isolation is your own VPC or on-prem segmentation around the GPU serving cluster.

RAG poisoning, malicious content planted in a source document that later gets retrieved and treated as trusted context, targets the retrieval layer, not the model host. Access control and validation on what gets indexed matters equally across every environment.
Stage 10 · cross-cutting

PHI & PII data protection

The technical control layer, not the compliance program. Policy, accountability, and audit ownership for regulated data live on the AI Governance Map; this is what enforces it in the pipeline.

AWS

Comprehend Medical and Comprehend's PII detection run as a pipeline step redacting protected fields; Macie inventories sensitive data already sitting in S3. A signed BAA with AWS is a precondition for PHI in Bedrock; confirm the specific model is in scope.

Azure

AI Language's PHI/PII detection (Text Analytics for Health) runs as a pipeline step, redacting or tokenizing protected fields. AI Search's document-level ACLs mean retrieval only surfaces chunks the requesting identity is authorized to see. A signed BAA with Microsoft is a precondition for PHI in Azure OpenAI or Foundry.

GCP

Cloud DLP (Sensitive Data Protection) for PII/PHI detection and redaction as a pipeline step, with de-identification templates reusable across the pipeline. A BAA with Google is a precondition for PHI in Vertex AI.

OCI

PII detection is one of the three protections built into OCI Guardrails (see Stage 9), identifying names, emails, phone numbers, and similar sensitive fields as a pipeline step. Encryption at rest is on by default across OCI storage services regardless.

Self-hosted / open-weight

De-identification via an open tool (Microsoft Presidio, or a PHI-tuned open NER model) run as the same kind of pipeline step, self-maintained. Disk and transport encryption are your own responsibility; nothing is on by default the way it is in a managed cloud service. No BAA applies since there's no third-party processor, but that shifts the entire compliance burden onto your own controls and audit evidence rather than removing the requirement.

Minimum necessary access and an immutable audit trail of who or what touched PHI are HIPAA requirements regardless of hosting. Hosting choice changes who implements the control, not whether it's required.
Stage 11 · cross-cutting

Observability & evaluation

Whether any of the above is working, and whether it's still working after the next model or index update.

AWS

CloudWatch plus X-Ray for distributed tracing across the pipeline, retrieval and generation latency broken out individually. X-Ray is transitioning to OpenTelemetry as its primary instrumentation standard, worth building on directly rather than the legacy SDK.

Azure

Monitor plus Application Insights for distributed tracing, with retrieval latency, generation latency, and per-tool-call latency broken out individually. AI Foundry's built-in evaluation and tracing for agent runs, with alerting when groundedness or relevance scores degrade.

GCP

Cloud Trace plus Cloud Monitoring for distributed tracing and metrics across the pipeline, with the same latency-breakdown pattern as the other providers.

OCI

Application Performance Monitoring (APM) for distributed tracing and latency breakdown across the pipeline.

Self-hosted / open-weight

OpenTelemetry instrumentation exported to a self-hosted or managed backend (Grafana, Jaeger). Langfuse or Arize Phoenix for LLM-specific tracing and evaluation. Prometheus and Grafana for GPU utilization, queue depth, and serving-stack metrics; vLLM exposes Prometheus metrics natively.

Logs and traces are themselves a PHI exposure surface if you're not careful. A stack trace or a debug log that captures the full prompt will capture any PHI that was in it. Redaction policy for observability data needs to match redaction policy for the data itself, across every environment.
Stage 12 · cross-cutting

Disaster recovery & continuity

What happens to the index, the weights, and the running service when something breaks.

AWS

OpenSearch and most managed vector stores lack point-in-time index restore; re-indexing from the source document store is the real recovery path. Bedrock-hosted models inherit AWS's regional redundancy; multi-region endpoint deployment is a separate decision.

Azure

AI Search has no built-in point-in-time restore for the index itself; re-indexing from the source document store is the actual recovery path. Foundry-hosted models inherit Azure's regional redundancy; multi-region deployment is a separate decision.

GCP

Same pattern: Vertex AI Vector Search has no native point-in-time restore, source-document re-indexing is the recovery path. Vertex AI-hosted models inherit GCP's regional redundancy.

OCI

Oracle Database 23ai's native backup and point-in-time recovery covers vector data stored in-database, a genuine difference from the other three, since the vectors live inside the database rather than a separate index.

Self-hosted / open-weight

Same principle as the managed clouds: back up the source documents and treat the vector index as rebuildable, unless the re-embedding cost at your data volume makes a direct index snapshot worth it. Version and store model weights and the exact serving configuration in a model registry with checksums, since "which exact checkpoint was running when this output was generated" is both an operational and an audit question.

Stage 13 · cross-cutting

Capacity & scaling

The architecture question underneath cost: can this handle load, and how far ahead do you need to plan for it. Cost modeling itself lives on the AI FinOps Map; this is what determines whether capacity is even available to buy.

AWS

Provisioned Throughput reserves capacity ahead of time; on-demand avoids that but comes with TPM/RPM rate quotas requiring an increase request well ahead of launch. Cross-region inference routes traffic across regions to dodge regional capacity limits at no added charge, a genuine differentiator here.

Azure

Provisioned Throughput requires reserving capacity ahead of time, and regional availability, not budget, is often the actual constraint. Pay-as-you-go avoids that reservation lead time but comes with TPM/RPM rate quotas needing an increase request well ahead of launch. Foundry deployments are provisioned capacity, not elastic by default.

GCP

Same shape: provisioned throughput for predictable capacity, pay-as-you-go with per-model rate quotas otherwise. Regional availability of specific Gemini model versions is often the binding constraint, same pattern as the other two clouds.

OCI

Capacity and quota mechanics follow the same general shape as the other clouds; verify current provisioned-throughput and rate-limit specifics directly against OCI documentation before planning a launch around them.

Self-hosted / open-weight

GPU procurement lead time is the real constraint here. Buying or leasing H100/H200-class GPUs can run multi-month lead times during tight supply cycles; renting from a GPU cloud (Lambda, CoreWeave, RunPod) trades that lead time for less capacity control and variable pricing. On the serving side, vLLM or TGI scale horizontally behind a load balancer, with continuous batching used to maximize throughput per GPU before adding more hardware. KV-cache memory, not raw compute, is usually the actual ceiling on concurrent requests per node.

Capacity planning has to happen months before a launch across every environment. What changes is the actual bottleneck: quota approval on a managed cloud, GPU hardware availability if self-hosting.
Stage 14 · cross-cutting

Data lineage & source versioning

Which exact source document, and which exact embedding model version, produced the chunk that ended up in a given response. Easy to skip until an incident or an audit asks the question and there's no answer.

AWS

Glue Data Catalog with Lake Formation for lineage tracking across source systems feeding ingestion. Managed vector stores generally lack native index versioning, so the same alias-swap pattern applies: build new, swap the pointer, retain the old for rollback.

Azure

Microsoft Purview for lineage and cataloging across the source systems feeding ingestion, tracking which document version fed which index generation. AI Search doesn't version indexes natively, so the common pattern is index aliasing: build new, swap the alias, retain the prior index for rollback.

GCP

Dataplex for lineage and cataloging across source systems. Same alias-swap pattern for the vector store itself, since Vertex AI Vector Search doesn't version indexes natively either.

OCI

OCI Data Catalog for lineage and cataloging across source systems feeding ingestion, tracking which document version fed which index generation.

Self-hosted / open-weight

No managed lineage catalog. Typically DVC (Data Version Control) or a plain metadata table alongside the vector store, recording source document hash, ingestion timestamp, and which embedding model version produced each chunk's vector. Same alias-swap pattern as every managed cloud above for the vector store itself, just self-implemented: build a new collection, swap the pointer, retain the old collection for rollback.

This is what ties disaster recovery and observability together. It's tempting to treat lineage as optional right up until an incident needs an answer to "which version produced this" and there isn't one.
