Data Strategy

Beyond the storage architecture question: the operating model behind who owns data, self-service and literacy for the rest of the organization, metadata and lineage, real-time versus batch as an economic decision, build versus buy for the data stack, and whether the data itself is a product worth monetizing, alongside warehouse versus lakehouse versus mesh, master data management, and data quality as an AI prerequisite.

General data strategy patterns, not a technology recommendation. The right architecture and operating model depend on organizational structure and data maturity more than on which pattern is currently trending.
Framework

Warehouse, lakehouse, or mesh

The architectural choice most data strategy conversations start with. It is a small part of the strategy, not the whole of it. Definitions first, then the tradeoff.

PatternWhat it isFits whenStruggles when
Data warehouseA central repository holding structured, pre-cleaned data, modeled and indexed for fast BI and reporting queries.Structured, well-understood reporting needs, a single team can reasonably own data quality centrallyData sources are highly heterogeneous or domain ownership needs to be distributed
Data lakehouseCheap, flexible storage for raw data in any format, with a warehouse-style query and schema layer built on top of it.Mixed structured and unstructured data, need for both BI and ML workloads on the same underlying dataOrganizational discipline around schema and quality is weak. A lakehouse without governance becomes a swamp fast
Data meshA decentralized operating model: each business domain owns, publishes, and is accountable for its own data as a product, instead of one central team owning all of it.Large organization with independent domains, each with the capacity to own their own data productApplied to an organization too small to staff domain-level data ownership. The coordination overhead exceeds the benefit
Ownership

Data as a product, and who staffs it

The mindset under data mesh, useful even in organizations that never adopt the full mesh model.

Treated as a project, a pipeline gets built once to answer a question and then slowly rots as the source system changes underneath it. Nobody owns noticing the drift, so the first sign is a broken report and an escalation. Treated as a product, a dataset has a named owner, a quality bar, a published contract (schema, freshness, what each field means), and a way to retire it. It is the discipline you already apply to an internal API, applied to data.

Then there is the staffing question. A central data team gives consistent standards and one point of accountability, and becomes a bottleneck once more teams depend on it than it can serve. Data engineers embedded in each domain sit closer to the business and move faster, and their standards drift apart without a strong shared platform underneath. Most organizations end up with both: a central platform team that owns tooling and standards, and embedded engineers who apply them. That is fine. What goes wrong is never deciding, so hiring decides by accident and nobody can say who owns what.

Master data

The golden record problem

The same customer lives in a CRM, a billing system, a support tool, and the product database, each with its own ID, update cadence, and partial view. No one system is right about everything.

Picking one system as the master for the whole record rarely works. Decide authority field by field instead, and let the merge logic follow that map.

FieldAuthoritative sourceWhy that one
Legal name and billing addressBilling systemIt is what invoices and tax filings use, and errors there cost money directly
Payment statusBilling systemThe only system that sees payments clear
Account owner and segmentCRMSales maintains it, and territory and commission depend on it
Product usage and active seatsProduct databaseMeasured, not entered by hand
Open issues and satisfactionSupport toolWhere the interactions actually happen
Primary contact emailUsually the CRM, with the product as fallbackThe one most often contested. Write the rule down, because both teams will assume theirs wins
Contracts

What a data contract has to specify

"Data contract" gets used loosely. A schema on its own is not one. Consumers build against it anyway, because it is the only documentation they have, and they break without warning the first time it changes upstream.

ElementWhat it commits toWithout it
SchemaField names, types, and which fields can be nullConsumers guess, and guess differently
MeaningA plain-language definition of each field, including units and edge casesTwo teams report different revenue from the same column
FreshnessHow current the data is guaranteed to be, and what happens when it is lateA dashboard silently shows yesterday's numbers as today's
Quality rulesThe checks the producer runs before publishingBad data is found by the consumer, usually in front of an executive
Change and deprecation policyNotice period for breaking changes and how old versions are retiredEvery upstream change is an outage for someone downstream
OwnerA named person or team, published where consumers can find itThe contract lives in one engineer's memory and leaves with them

The Open Data Contract Standard, listed in the standards table below, turns this into a file that can be checked automatically in CI.

Metadata

Catalog and lineage: the layer that gets skipped

What data do we have, what does it mean, and what breaks if I change it? In organizations that otherwise have their data strategy in order, this is often still the weakest layer.

It gets skipped because the pain is spread thin. A five-hop manual trace when a report breaks. A schema change shipped without knowing that six downstream jobs depend on it. An analyst who can't tell whether a dataset is still owned or safe to use. None of that is a single dramatic incident, so it stays below the funding line year after year.

A catalog makes data findable and says who owns it and whether to trust it. Lineage traces the path from source system to dashboard or model, so a broken pipeline can be traced to every consumer in minutes. Both pay off twice more on this page: you can't run old and new platforms in parallel during a migration if you don't know what depends on what, and an AI agent that can't see schema, lineage, and ownership will guess.

Buy this, almost without exception. It is a mature, competitive market. The real decision is how to keep metadata alive from the first day, tagged and enforced and shown where people already work, instead of a wiki page that is stale within a quarter.

Decisions

The calls a data strategy has to make

Each has a sensible default. The strategy is mostly a record of where you deviate from it, and why.

DecisionDefaultDeviate when
Real-time or batchBatch, refreshed as often as the slowest real decision needsThe value of the data decays within minutes: fraud detection, live personalization, operational alerting. Streaming for a report read weekly is an ongoing tax, the data equivalent of an extra nine of availability nobody needed. See Reliability as an Economic Decision
Build or buyBuy ingestion, transformation tooling, catalog, and BI. These are mature markets and building recreates a worse versionThe data product itself is the differentiator. Even then, buy the infrastructure underneath. The test from Build vs Buy applies: would you lose deals or margin without owning this?
How to migrate between patternsRun the new pattern beside the old for a few domains, prove value, then expand, the strangler-fig approach from Legacy Modernization ExecutionRarely. A single multi-quarter migration with nothing delivered along the way runs out of executive patience long before it finishes
Self-service for non-engineersA curated set of modeled datasets with guardrails, plus trainingNever hand out tool licenses alone. That produces a spread of dashboards answering the same question differently, which is worse than the bottleneck it was meant to fix
Sell or share data externallyNoYou hold data someone else would pay for and can carry the privacy, security, and packaging cost. Most companies can't, but it should be a considered no rather than a question nobody asked
AI

Data quality is the AI prerequisite nobody budgets for

This page and the data controls on the AI Governance Map describe the same problem from two altitudes.

An AI system trained on or retrieving from poorly owned, poor-quality data inherits every one of its problems, at scale, and with less visibility into the failure than an analyst working the same data by hand would have. The good news is that the fix is the same work whether or not AI is on the roadmap. An organization with real data product discipline already has most of what AI governance asks of training and retrieval data, so there is no need to frame it as a separate project to finish first.

Reference

Standards and open formats worth knowing

The data stack has converged on a few open standards in the last three years. Choosing them lowers switching cost later, which is the build-versus-buy argument applied to formats.

StandardWhat it isWhy it matters
Open table formats: Apache Iceberg, Delta Lake, Apache HudiTable layers over files in object storage that add transactions, schema evolution, and time travelThe same tables can be read by several engines, so the lakehouse is no longer tied to one vendor's compute
Open Data Contract Standard (ODCS), maintained by Bitol under the Linux FoundationA YAML standard for data contracts: schema, quality rules, service levels, ownership, and termsMakes the contract definition above checkable in CI instead of a document nobody reads
OpenLineageAn open specification for emitting lineage events from pipelines and toolsLineage collected from many tools into one graph without per-vendor integrations
DAMA-DMBOK (DAMA International)The reference body of knowledge for data management disciplinesA shared vocabulary for governance, quality, metadata, and master data roles
DCAM (EDM Council)A data management capability assessment modelA way to benchmark maturity that regulators and auditors in financial services recognize
Where to start

The first quarter, if the strategy so far is a slide

Narrow and concrete beats comprehensive. Each step produces something a skeptic can check.

  1. Name owners for the twenty most used datasetsUsage logs from the warehouse or BI tool will tell you which twenty. An owner is a person, not a team alias.
  2. Write the field-level authority map for one entityCustomer is usually the right first choice, because everything else joins to it.
  3. Put contracts on the five datasets with the most consumersAll six elements from the contracts table, published where consumers look.
  4. Turn on lineage for those fiveEnough to answer what breaks if this changes, for the data that matters most.
  5. Write down the operating model you actually haveCentral, embedded, or both, and who owns which standard. Then decide whether to keep it.
