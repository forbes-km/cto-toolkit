Common controls: map once, satisfy many

The actual current practice, and the reason a dedicated GRC layer earns its keep once an organization is answering to more than one framework.

Practice

Build one internal control set, then map each control to every external framework it satisfies, SOC 2, ISO 27001, HIPAA, PCI-DSS, GDPR. One access review, one screenshot, one policy document gets reused everywhere it's relevant, collected once and referenced by every audit that needs it, not re-produced fresh for each one.

Common failure mode

Treating each framework as its own separate project with its own evidence collection cycle, so the same access review gets re-screenshotted three times a year for three different auditors, and the organization never builds a control library that compounds in value as more frameworks get added.

This is what most current GRC and compliance automation tooling is built around, not automating any single framework, automating the reuse of evidence across all of them.

Centralized versus distributed GRC

A real, live organizational design question, and one that usually gets decided by accident rather than on purpose.

Centralized

One function owns governance, risk, and compliance end to end: a single risk register, one consistent methodology, one team an auditor talks to. The risk: that function can drift distant from the technical and threat context each domain needs to assess its own risk accurately.

Distributed

Security owns security compliance, legal owns privacy compliance, finance owns financial controls, each close to its own domain's real context. The risk: findings don't reliably reach each other, and a genuinely cross-cutting risk, AI governance is the clearest current example, can fall through every function's boundary at once because it isn't fully owned by any of them.

Most real organizations land somewhere in between: a small central function owning the common control library and the risk register, with domain owners responsible for implementing controls within their own area against it. The failure mode is landing there by accident rather than deciding it deliberately, the same distinction Role Boundaries makes for CTO, CIO, CISO, and CPO scope generally.

Continuous compliance tooling, briefly

What this category of tool changes, not a specific product recommendation.

A newer category of GRC tooling automates evidence collection and control monitoring continuously, connected directly to the underlying systems, rather than producing a point-in-time snapshot assembled by hand in the weeks before an audit. The practical shift: compliance posture becomes something the organization already knows on any given day, instead of something it scrambles to reconstruct once a year. This doesn't remove the need for judgment, validating evidence, handling exceptions, talking to an auditor still requires a person, but it removes most of the repetitive manual collection that used to consume the weeks before every audit cycle.

Signs GRC is fragmented rather than functioning

Patterns that show up when governance, risk, and compliance exist as activities but not as a coordinated function.

  • The same evidence gets collected fresh for each separate audit instead of drawn from a reusable control library
  • A risk finding from one function, security, never reaches another function that needed to know about it, privacy, legal
  • No single risk register exists; each function tracks its own risks in its own spreadsheet with no shared view
  • Compliance posture is only really known in the weeks right before an audit, not on any given ordinary day
  • Whether GRC is centralized or distributed was never deliberately decided, it's just whatever happened as the organization grew
