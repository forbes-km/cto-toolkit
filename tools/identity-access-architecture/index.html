Identity & Access Architecture

Identity is the first-move recommendation in the Zero-Trust Maturity model and the control every other control depends on. This page is the standalone treatment: the populations most programs forget, a reference architecture across the major platforms, the lifecycle process that decides whether the architecture works, and the sequence to follow when everything is weak.

Provider feature names change frequently. The layer structure is stable; verify the current product name and capability against the provider's documentation before designing to it. See Building a Security Program for where identity sits in the wider sequence and Data Governance & Privacy for the access-to-data side of the same problem.
Framework

Identity is the control plane, not a service

Every other security control assumes the request came from who it says it did. If that assumption is weak, segmentation, detection, and encryption are all decorating an open door.

Most estates have at least four identity populations, and most identity programs are built for only the first. The others are where the breaches happen.

Lifecycle

Joiner, mover, leaver: the process that decides whether the architecture works

The most sophisticated Conditional Access policy in the world does nothing about the contractor who left eight months ago and still has a working account.

Where it fails

Access is granted by ticket, on request, by whoever is asked. Nobody removes access when someone changes role, so tenure equals entitlement. Offboarding disables the directory account but not the twelve SaaS apps with local accounts, the shared service credential the person knew, or the API key they created. The access review is an annual spreadsheet that every manager approves in full because rejecting anything means explaining it.

What good looks like

Birthright access is defined per role and granted automatically from the HR event. Anything beyond birthright is requested through an access package with a named approver and an expiry. A mover event triggers removal of the old role's entitlements, not just addition of the new. A leaver event is a single action that cascades to every federated app within minutes, and there is a report of what could not be cascaded, which is the list of local accounts still to be eliminated. Access reviews are quarterly, scoped to privileged and sensitive entitlements, and the default on no response is removal.

Non-human identity

The population that is now larger than the workforce

In most cloud estates service principals, roles, keys, and automation identities outnumber people three to one and nobody owns the inventory. AI agents are adding to this fast, and they act with whatever identity they are given.

The questions to ask, in order:

  1. How many existPull the full list of service principals, IAM roles, service accounts, and API keys from every cloud tenant and the CI system. If the number is a surprise, that is the finding.
  2. Which have an ownerEvery non-human identity needs a named human owner and a purpose. Anything without one is a candidate for disablement after a quarantine period.
  3. Which use long-lived secretsA client secret or access key that does not expire is a credential that will eventually be in a repository, a log, or a former employee's laptop. Migrate to managed identity or federated tokens; where impossible, vault and rotate.
  4. Which are over-privilegedMost workload identities were granted Contributor or PowerUser because it worked. Use the platform's unused-access analysis to shrink them to what they call.
  5. Which can reach production from outside itCI runners and developer tooling that hold production credentials are the standard path from a compromised laptop to a production breach.
  6. What identity do agents act withAn AI agent that calls tools does so as something. If that something is a broadly-scoped service principal, the agent's judgment is now a security control. Give agents their own scoped identities, short-lived, with the same review cadence as privileged humans.

Week one

The single artifact that tells you the most

For a new CTO, an acquirer, or an auditor, one export answers most of the question of how seriously identity has been taken.

What to pull

The list of every account holding a privileged role in each cloud tenant and the directory, with whether the assignment is permanent or eligible, when it was last used, and whether the account has phishing-resistant MFA registered. Then the same for service principals with owner-level rights. It takes an hour and requires no tooling beyond what the platform provides.

How to read it

More than a handful of permanent global admins, any of them shared or belonging to people who have left, any without strong MFA, or any service principal with tenant-wide write access and a non-expiring secret: each is a finding in its own right, and together they say the identity layer has been administered rather than architected. That reading should shape the first quarter's security priorities regardless of what the security roadmap deck says.

Common pitfall

Buying the identity platform and calling it done

Most organizations that fail on identity already own the right products. The failure is in the process, the scope, and the exceptions.

  • MFA is enforced, but the legacy authentication protocols that bypass it are still enabled
  • Conditional Access exists, but the policy has forty exclusions and the exclusion group is the one everyone ends up in
  • PIM is deployed for global admin, but the subscription and resource-group owners are still permanent
  • The HR feed is connected, but contractors are not in HR, so the largest leaver risk is unmanaged
  • Access reviews run, but the approval rate is 100 percent, which means nobody is reviewing
  • The break-glass account exists and has never been tested, or has been tested and used routinely because it is convenient
  • Secrets are in a vault, but the application also has a copy in an environment variable that was never removed
