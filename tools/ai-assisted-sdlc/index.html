AI-Assisted SDLC & Delivery Pipelines

AI and the Engineering Operating Model covers what AI changes for engineers: review, skills, and measurement. This page covers what it changes for the delivery system: each stage of the lifecycle, the pipeline, the permissions agents run with, and the controls that let AI-written code reach production safely.

Tool names, features, and prices in this area change monthly. The controls do not. Product details are stated as of October 2026 and cited; verify against the vendor's current documentation before relying on them. For which AI initiatives to fund, see AI Portfolio Management; for AI governance across the business, the AI Governance Map.

Pipeline guardrails for AI-written code

Policy that relies on memory does not survive the first deadline. Each control below is enforced by the pipeline, so it holds whether the change came from a person, an assistant, or an agent.

  1. Keep changes small, by ruleSet a diff-size threshold above which a pull request must be split or gets an extra reviewer. DORA's 2025 research names working in small batches as one of the seven capabilities that decide whether AI helps or hurts[4][5]. Agents produce large diffs cheaply. Review capacity does not scale with them.
  2. Make security scanning blockingStatic analysis, secret scanning, and dependency scanning run on every change and fail the build on high-severity findings. In Veracode's 2025 testing of more than 100 models on 80 tasks, 45 percent of generated code samples introduced a security flaw, with failure rates of 86 percent for cross-site scripting and 88 percent for log injection[2]. A warning nobody has to act on does not count.
  3. Put an admission gate on new dependenciesEvery package an AI suggests must exist, be resolved through your registry proxy, and pass malware and vulnerability checks before it lands. Across 576,000 generated samples, 19.7 percent of recommended packages did not exist. When 500 of the prompts that produced them were rerun ten times, 43 percent of the hallucinated names came back every time[6]. Repeatable names are the problem: an attacker can register them in advance, a pattern since named slopsquatting[7]. Treat a dependency the developer has never heard of as a design decision, not a line of code.
  4. Record provenance on every changeLabel AI-assisted and agent-authored commits so defects, incidents, and security findings can be broken down by origin later. Open-source projects are converging on a commit trailer: the Linux kernel asks contributors to add an Assisted-by tag and does not allow an AI to add a Signed-off-by line[8]; Fedora's October 2025 policy encourages a similar Assisted-by trailer naming the tool[9]. Pair it with build provenance: SLSA Build Level 2 requires a hosted build platform that signs its provenance, and Level 3 adds isolation between builds[10].
  5. Separate the requester from the approverThe person who asked an agent for a change reviews it, but cannot be the approval that lets it merge. GitHub's cloud agent is built this way: it pushes only to its own branch, cannot approve or merge its own pull request, and the user who asked for it cannot approve it[3]. Add code owners for sensitive paths such as authentication, payments, and infrastructure, so those changes always reach the right reviewer.
  6. Govern the instruction filesRules files, agent instruction files, and assistant configuration steer every change the model makes, so they are code. Put them under code ownership and scan them for hidden characters. Pillar Security showed that invisible Unicode in a rules file could make Cursor and GitHub Copilot insert an attacker's script into generated code without mentioning it, and that the characters stayed invisible in pull request review[11]. OpenSSF publishes a security-focused guide for what those files should say[7].
  7. Harden the pipeline the agent runs inAgent-authored pull requests run workflows only after a human approves them. GitHub holds them by default, and since March 2026 lets administrators skip that approval, which means workflows can reach tokens and secrets without review[12]. Never run untrusted pull request content with privileged triggers: the August 2025 Nx compromise began with a workflow that allowed code injection through pull request titles under the pull_request_target trigger[13].
  8. Make AI-written tests prove somethingGenerated tests raise coverage numbers without necessarily testing anything. Require tests on changed lines, review assertions, and run mutation testing on the code that matters most. The question is not whether tests exist, but whether they would fail if the code were wrong.

Agent permissions: design around the lethal trifecta

Simon Willison's test is the clearest one available. An agent that has access to private data, is exposed to untrusted content, and can communicate externally can be tricked into stealing that data[1]. A coding agent usually has all three by default: your source code, issue text written by strangers, and network access. Remove at least one, every time.

ControlMinimum standardWhy
IdentityEach agent runs as its own identity, never on a person's token. Its actions are attributable in the audit logAttribution, revocation, and separation of duties all depend on knowing the agent from the person
CredentialsShort-lived tokens scoped to one repository and the minimum permissions. No production credentials, everA token issued for one purpose should not work for another. The MCP specification forbids servers from accepting tokens not issued to them and recommends minimal, incremental scopes[14]
Execution environmentAn ephemeral, isolated sandbox per task. Not a developer laptop that holds SSH keys, cloud credentials, and wallet filesIn the Nx compromise, malware ran on developers' machines and invoked locally installed AI command-line tools with their permission checks turned off to hunt for secrets[13]
NetworkOutbound access limited to an allowlist: the package registry proxy, the source host, the model endpointExfiltration needs a way out. GitHub's cloud agent restricts internet access by default for this reason[3]
Tools and MCP serversAn allowlist of approved servers, pinned versions, one repository per session where possible, and consent before any new local server runsIn May 2025, Invariant Labs showed that a malicious issue in a public repository could lead an agent using the GitHub MCP server to copy private repository data into a public pull request[15]. The flaw was the combination of permissions, not a bug in the server
Branch and mergeAgents push only to their own branch. Merge, workflow runs, and deployment need a humanKeeps the most consequential actions behind a person who can say no
Destructive actionsAgents cannot drop data, delete resources, or force-push. Development and production data are physically separateIn July 2025 an agent deleted the database behind a user's app during an explicit code freeze. The vendor rolled out automatic separation of development and production databases, pointed to its one-click project restore, and began work on a planning-only mode[16]
Logging and kill switchSession logs retained, linked from each commit, reviewable by security. One action revokes an agent's access everywhereWhen something goes wrong, the first questions are what it did and how to stop it

Cost and commercial terms

AI coding tools are moving from flat seats to metered usage, which turns developer tooling into a variable cost that behaves like cloud spend.

The clearest example: from June 1, 2026, GitHub Copilot usage consumes GitHub AI Credits, charged by input, output, and cached tokens at each model's published rate. Business seats stay at $19 and Enterprise at $39 per user per month, each including that amount in monthly credits, pooled across the organization, with budgets settable at enterprise, cost center, and user level. Code completions and next edit suggestions remain included; other usage, including AI code review, consumes credits, and code review also uses GitHub Actions minutes[27]. The heavier the agent use, the more of the bill is variable. Prices and terms change often; check the vendor's current page before budgeting.

DecisionWhat to do
BudgetSet a monthly budget per team or cost center from day one, with an alert at 80 percent. Treat it in the same review as cloud spend, per AI FinOps and Cloud FinOps
Unit economicsReport model spend per merged change and per agent session, next to lead time and change failure rate. Spend that rises while those stay flat is the signal to stop
Data termsEnterprise terms that exclude training on your code and prompts, a stated retention period, data residency where it matters, and audit logs you can export
IP termsIP indemnity for generated output, and filtering for suggestions that match public code. Check what the indemnity requires you to have switched on
Model and vendor choicePrefer tools that let you choose and change models, and keep instruction files in a tool-neutral form, so a renewal is a negotiation, not a migration. See SaaS Contract and Renewal Negotiation

For an organization where assistants are already in use and agents are arriving. Each step produces evidence before the next one starts.

Red flags

Signs the controls are behind the tools

Any two of these usually means agents are running at a level the controls were never designed for.

  • Agents run on developer laptops that hold SSH keys, cloud credentials, or production access
  • Nobody can say what share of last month's merged changes were written by an agent
  • Security scans warn but do not block, and the warnings are routinely ignored
  • New dependencies land without anyone checking that the package existed a month ago
  • Rules and instruction files have no owner and change without review
  • The person who asked the agent for a change is also the one who approves it
  • Agent workflows run without approval, and the pipeline holds secrets those workflows can read
  • Model spend has no budget, owner, or alert
  • Change failure rate was never measured before the rollout, so nobody can tell whether it moved
Common pitfall

Giving the agent the developer's keys

The fastest way to adopt agents is to install one on every laptop and let it act as the developer. It is also the setup behind the worst outcomes on this page.

What it looks like

Engineers run a local agent with the permission prompts turned off because they slow things down. The agent works in the same environment as the engineer's SSH keys, cloud credentials, and checked-out private repositories, and it reads issues, web pages, and package code written by strangers. Nothing it does is attributable to anything but the engineer. When a poisoned instruction or a malicious package arrives, the agent has everything it needs to send secrets out, and the logs show the engineer did it.

The counter-move

Agents get their own identity and an ephemeral sandbox per task, with scoped short-lived tokens and an egress allowlist. Local agents run inside a container or development environment that holds no standing credentials, with permission prompts left on for anything outside the working tree. Changes leave the sandbox only as a pull request on the agent's own branch, through the same gates as everything else. The platform team owns this as a golden path, per Platform Engineering, so the safe way is also the easy way.
