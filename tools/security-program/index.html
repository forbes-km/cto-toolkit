Building a Security Program

How to stand up a security function from little or nothing, sequenced by what reduces risk first, as distinct from scoring a program that already exists.

This covers building the program. See Zero-Trust Maturity for scoring a program once it exists, evaluated on evidence rather than stated policy, and Governance, Risk & Compliance for how this program connects to a broader multi-framework compliance effort.
Framework

Sequencing: what to build first

Security programs built in the wrong order spend budget on certifications before basics are solid, then fail an audit or a real incident on something the certification never checked.

StageFocusWhy it sits here in the sequence
FoundationMFA everywhere, least-privilege access, asset inventory, basic loggingEverything else depends on this being in place rather than aspirational
VisibilityCentralized logging, vulnerability scanning, dependency trackingYou can't manage what you can't see; this precedes any formal certification effort
ProcessIncident response plan, vulnerability management SLA, access review cadenceTurns visibility into action with defined ownership and timelines
CertificationSOC 2, ISO 27001, or industry-specific frameworksDocuments what should already be true; pursuing it earlier produces a program built for the audit rather than for risk
1

Where security reports, and how it's funded

Organizational placement determines whether security has authority or exists to be consulted and overruled.

Practice

Security leadership with a direct line to the CEO, CTO, or board, rather than buried three levels inside engineering where its priorities compete for the same budget and headcount as feature delivery and consistently lose. Funded as its own line item rather than a rounding error inside another team's budget.

Common failure mode

Security reporting to the VP of Engineering whose bonus is tied to shipping velocity, which creates a structural conflict every time a security requirement would slow a release. The person deciding the tradeoff has an incentive on only one side of it.

2

The certification trap

Chasing SOC 2 or ISO 27001 before the underlying practice exists produces a certification that doesn't mean what it's supposed to mean.

Practice

Treat the certification as documentation of an existing, functioning program rather than the goal itself. If the auditor's checklist is the first time a control gets implemented, it'll be the first thing that lapses once attention moves elsewhere after the audit passes.

Common failure mode

A clean SOC 2 report sitting alongside weak day-to-day practice, because the control existed for exactly the audit window and nowhere else. This is discoverable, and it's the kind of gap a technology diligence process is built to find.

3

DevSecOps: where security enters the pipeline

Security that only reviews code after it's written catches less and creates more friction than security embedded earlier.

Practice

Automated scanning (SAST, dependency checking, secret detection) running in CI on every commit, with findings surfaced to the engineer who wrote the code within minutes rather than batched into a security review weeks later when context is gone and the fix costs more.

Common failure mode

A security team that reviews finished features right before release, which makes every finding an emergency, teaches engineers to see security as an obstacle rather than a partner, and pushes fixes to be rushed under deadline pressure.

4

Building without headcount

Early-stage companies rarely get a security team on day one. The sequencing still matters even with one part-time person or none.

Start with the foundation-stage items above; they cost discipline more than headcount: enforce MFA, remove standing admin access, keep a current inventory of what systems exist and who owns them. A fractional security advisor or a well-scoped external assessment can substitute for a full-time hire through the visibility stage; process and certification need dedicated ownership once the company is large enough that a security incident would be existential.

5

Third-party and vendor risk as part of the program

Verizon's 2025 Data Breach Investigations Report found a third party involved in 30 percent of breaches, double the year before. A security program that stops at the company's own systems is scoped to the wrong boundary.

Practice

Every vendor with access to production systems or sensitive data gets a security review before signing, using the same evidence-over-policy discipline covered in the certification trap above. Track which vendors hold what data, and get notification obligations for a vendor's own breach written into the contract.

Common failure mode

Security review happens for major platform vendors and gets skipped for the small SaaS tool a team signed up for with a credit card, which is exactly the kind of vendor least likely to have a mature security program and most likely to be the entry point when something goes wrong.

6

The human element

Most incidents start with a person rather than a zero-day. Awareness training exists to address this and usually doesn't.

What changes behavior

Short, frequent, specific training tied to real incidents the company or its industry has seen, plus simulated phishing that's used to identify where more support is needed rather than to publicly shame whoever clicked. The goal is a workforce that reports a suspicious email in minutes instead of hiding a mistake.

The checkbox version

An annual training video nobody remembers a week later, run once for compliance purposes and never referenced again. It satisfies an audit requirement and does close to nothing for risk, which is the same gap the certification trap describes, applied to people instead of controls.

7

What the program looks like at different stages

The sequencing above holds at every size. What changes is how much of it is a dedicated person versus a shared responsibility.

StageWhat's realistic
Under 50 engineersFoundation stage owned by engineering leadership directly, no dedicated headcount yet. A fractional advisor for anything requiring specialized judgment.
50 to 200 engineersFirst dedicated security hire, typically a generalist covering foundation and visibility stages. Certification work, if customer-driven, usually needs external audit support.
200 to 1,000 engineersA small team with a named leader reporting per the authority guidance above, specialization beginning (application security separate from infrastructure security).
1,000-plus engineersA full function with dedicated roles across the domains this page and Security & Compliance Maturity describe, and enough scale that the vendor risk program above needs its own owner.

What attackers are actually doing

Sequence the program against how breaches happen, not against a framework's table of contents. Figures are from Verizon's 2025 Data Breach Investigations Report, based on more than 12,000 confirmed breaches.

FindingWhat it means for sequencing
Credential abuse was the leading initial access vector, at about 22 percent of breachesPhishing-resistant MFA and removing standing admin access belong in the first 30 days
Exploitation of vulnerabilities was about 20 percent, up roughly a third on the prior year, with edge devices and VPNs heavily targetedAn enforced patch deadline for known-exploited vulnerabilities on internet-facing systems, measured weekly
Third-party involvement doubled to 30 percentVendor inventory and access review before, not after, the certification effort
Ransomware was present in 44 percent of breaches, and in the large majority of breaches at smaller organizationsOffline or immutable backups with a tested restore are foundation-stage work, not resilience polish
9

The first 180 days, sequenced

A concrete plan that follows the stages above. Days are guides; the order matters more than the pace.

WindowDeliverables
Days 0 to 30Phishing-resistant MFA for administrators, email, and remote access; standing admin rights removed; asset and SaaS inventory started; endpoint detection deployed; backups verified offline or immutable, with one real restore
Days 31 to 90Central logging with at least 12 months retention for security-relevant sources; external attack surface scanning; a 14-day deadline for known-exploited vulnerabilities on internet-facing systems; an incident response plan and one tabletop exercise; vendor inventory with data access mapped
Days 91 to 180Secret scanning, dependency scanning, and static analysis in CI; quarterly access reviews with evidence; phishing simulation used for coaching; a risk register tied to the risk appetite; a gap assessment against NIST CSF 2.0 or CIS Controls IG1
After 180 daysCertification if customers require it, now documenting controls that already run; specialization of the team as described in section 7

Frameworks, and what each one is for

Choosing a framework is choosing an audience. Most organizations use one as the internal backbone and map the others to it, as described on Governance, Risk & Compliance.

FrameworkWhat it isUse it when
NIST Cybersecurity Framework 2.0 (2024)Outcome-based framework with six functions; 2.0 added GovernYou need a program backbone and a common language with the board
CIS Critical Security Controls v8.118 controls and 153 safeguards, grouped into three implementation groups; IG1 is essential cyber hygieneYou need a concrete, prioritized first-year checklist
ISO/IEC 27001:2022A certifiable information security management system with 93 Annex A controls; 2013-version certificates expired on October 31, 2025International or enterprise customers ask for certification

Checklist

Signs the program is theater

Patterns that show up when a security program looks complete in documentation and isn't reflected in daily operation.

  • Policies exist and are current, but engineers can't describe what they do differently because of them
  • A clean audit report alongside known unpatched vulnerabilities or unreviewed access grants
  • Security reviews happen only at release time, never earlier in the development process
  • No one can say when the last access review happened or produce evidence it occurred
  • Security funding and headcount decisions are made by the same leader whose other priorities compete directly with security requirements
  • Vendor security review happens for large platform contracts and gets skipped for anything signed up with a credit card
  • Administrator and email access use SMS or app codes rather than phishing-resistant MFA
  • No written deadline exists for patching known-exploited vulnerabilities on internet-facing systems, or nobody measures it
Reference only. Breach statistics are from Verizon's 2025 Data Breach Investigations Report; framework details reflect NIST CSF 2.0, CIS Controls v8.1, ISO/IEC 27001:2022, the AICPA Trust Services Criteria, HITRUST CSF, PCI DSS v4.0.1, and the CMMC program as of September 2026. Security program requirements vary by industry, regulatory exposure, and company scale; adapt sequencing accordingly.
