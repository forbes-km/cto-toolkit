Building a Security Program

How to stand up a security function from little or nothing, sequenced by what reduces risk first, as distinct from scoring a program that already exists.

This covers building the program. See Zero-Trust Maturity for scoring a program once it exists, evaluated on evidence rather than stated policy, and Governance, Risk & Compliance for how this program connects to a broader multi-framework compliance effort.
Framework

Sequencing: what to build first

Security programs built in the wrong order spend budget on certifications before basics are solid, then fail an audit or a real incident on something the certification never checked.

StageFocusWhat comes after, not before
FoundationMFA everywhere, least-privilege access, asset inventory, basic loggingEverything else depends on this being real, not aspirational
VisibilityCentralized logging, vulnerability scanning, dependency trackingYou can't manage what you can't see; this precedes any formal certification effort
ProcessIncident response plan, vulnerability management SLA, access review cadenceTurns visibility into action with defined ownership and timelines
CertificationSOC 2, ISO 27001, or industry-specific frameworksDocuments what should already be true; pursuing it earlier produces a program built for the audit, not for actual risk
1

Where security reports, and how it's funded

Organizational placement determines whether security has real authority or exists to be consulted and overruled.

Practice

Security leadership with a direct line to the CEO, CTO, or board, not buried three levels inside engineering where its priorities compete for the same budget and headcount as feature delivery and consistently lose. Funded as its own line item, not as a rounding error inside another team's budget.

Common failure mode

Security reporting to the VP of Engineering whose bonus is tied to shipping velocity, which creates a structural conflict every time a security requirement would slow a release. The person deciding the tradeoff has an incentive on only one side of it.

2

The certification trap

Chasing SOC 2 or ISO 27001 before the underlying practice is real produces a certification that doesn't mean what it's supposed to mean.

Practice

Treat the certification as documentation of an existing, functioning program, not the goal itself. If the auditor's checklist is the first time a control gets implemented, it'll be the first thing that lapses once attention moves elsewhere after the audit passes.

Common failure mode

A clean SOC 2 report sitting alongside weak day-to-day practice, because the control existed for exactly the audit window and nowhere else. This is discoverable, and it's exactly the kind of gap a technology diligence process is built to find.

3

DevSecOps: where security enters the pipeline

Security that only reviews code after it's written catches less and creates more friction than security embedded earlier.

Practice

Automated scanning (SAST, dependency checking, secret detection) running in CI on every commit, with findings surfaced to the engineer who wrote the code within minutes, not batched into a security review weeks later when context is gone and the fix costs more.

Common failure mode

A security team that reviews finished features right before release, which makes every finding an emergency, teaches engineers to see security as an obstacle rather than a partner, and pushes real fixes to be rushed under deadline pressure.

4

Building without headcount

Early-stage companies rarely get a security team on day one. The sequencing still matters even with one part-time person or none.

Start with the foundation-stage items above, they cost discipline more than headcount: enforce MFA, remove standing admin access, keep an actual inventory of what systems exist and who owns them. A fractional security advisor or a well-scoped external assessment can substitute for a full-time hire through the visibility stage; process and certification need dedicated ownership once the company is large enough that a security incident would be existential.

5

Third-party and vendor risk as part of the program

Most breaches now originate through a vendor, not a direct attack on the company's own perimeter. A security program that stops at the company's own systems is scoped to the wrong boundary.

Practice

Every vendor with access to production systems or sensitive data gets a security review before signing, not after, using the same evidence-over-policy discipline covered in the certification trap above. Track which vendors hold what data, and require notification obligations for a vendor's own breach written into the contract, not assumed.

Common failure mode

Security review happens for major platform vendors and gets skipped for the small SaaS tool a team signed up for with a credit card, which is exactly the kind of vendor least likely to have a mature security program and most likely to be the actual entry point when something goes wrong.

6

The human element, done honestly

Most real incidents start with a person, not a zero-day. Awareness training exists to address this and usually doesn't.

What changes behavior

Short, frequent, specific training tied to real incidents the company or its industry has seen, plus simulated phishing that's used to identify where more support is needed, not to publicly shame whoever clicked. The goal is a workforce that reports a suspicious email in minutes, not one that's afraid to admit a mistake.

The checkbox version

An annual training video nobody remembers a week later, run once for compliance purposes and never referenced again. It satisfies an audit requirement and does close to nothing for actual risk, which is the same gap the certification trap describes, applied to people instead of controls.

7

What the program looks like at different stages

The sequencing above holds at every size. What changes is how much of it is a dedicated person versus a shared responsibility.

StageWhat's realistic
Under 50 engineersFoundation stage owned by engineering leadership directly, no dedicated headcount yet. A fractional advisor for anything requiring specialized judgment.
50 to 200 engineersFirst dedicated security hire, typically a generalist covering foundation and visibility stages. Certification work, if customer-driven, usually needs external audit support.
200 to 1,000 engineersA small team with a named leader reporting per the authority guidance above, specialization beginning (application security separate from infrastructure security).
1,000-plus engineersA full function with dedicated roles across the domains this page and Security & Compliance Maturity describe, and enough scale that the vendor risk program above needs its own owner.
Checklist

Signs the program is theater, not practice

Patterns that show up when a security program looks complete in documentation and isn't reflected in daily operation.

  • Policies exist and are current, but engineers can't describe what they do differently because of them
  • A clean audit report alongside known unpatched vulnerabilities or unreviewed access grants
  • Security reviews happen only at release time, never earlier in the development process
  • No one can say when the last access review happened or produce evidence it occurred
  • Security funding and headcount decisions are made by the same leader whose other priorities compete directly with security requirements
  • Vendor security review happens for large platform contracts and gets skipped for anything signed up with a credit card
Reference only. Security program requirements vary significantly by industry, regulatory exposure, and company scale; adapt sequencing accordingly.
