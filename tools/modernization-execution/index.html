Legacy Modernization Execution

How a migration gets run once the decision to modernize has been made. Distinct from deciding what to modernize, that's the Application Portfolio Management question, this is about the execution mechanics that determine whether the migration succeeds or stalls.

This covers execution mechanics. See Application Portfolio Management for deciding what to modernize in the first place, and Technology Diligence for assessing what's being inherited in an acquisition.
Framework

The strangler fig pattern

The dominant strategy for modernizing a live system without a high-risk, high-visibility cutover: grow the new system around the edges of the old one until the old one can be safely retired.

New functionality is built in the new system and routed to it, while remaining functionality continues running in the old system, with a routing layer (a proxy, a facade, a feature flag) directing each request to whichever system currently owns it. Over time, more capability migrates to the new system until the old system handles nothing and can be decommissioned. The old system shrinks gradually instead of being replaced in a single event, which is what makes this the lower-risk default over a full rewrite and cutover.

1

Cutover planning and rollback criteria

Every cutover, whether a full system swap or a single capability moving to the new system, needs a defined rollback trigger decided before the cutover happens, not improvised during it.

Practice

Specific, pre-agreed rollback criteria (error rate above X percent, latency above Y, a defined list of critical functions that must work correctly) checked immediately after cutover, with the rollback mechanism tested in advance, not assumed to work when it's needed under pressure.

Common failure mode

"We'll roll back if it looks bad" as the entire rollback plan, which under real pressure becomes a debate about whether it's bad enough yet, while customer impact accumulates during the debate.

2

Parallel-run validation

Before fully trusting the new system, run it alongside the old one and compare outputs on real traffic.

Practice

Shadow traffic sent to both systems, with outputs compared automatically and discrepancies flagged, for long enough to build genuine confidence, weeks for a low-volume system, potentially longer for something with meaningful seasonal or cyclical variation in the data it processes.

Common failure mode

A parallel run cut short because it's "looking fine so far," which misses the edge case that only shows up during month-end processing, a holiday traffic spike, or some other pattern the shortened window never covered.

3

Data migration sequencing

Moving the data is usually harder and riskier than moving the code, and it's where migrations most often go over budget and over timeline.

Practice

Migrate data incrementally where possible, validated in batches with reconciliation checks against the source, rather than one large migration event. Keep the old system's data as the system of record until the new system has been validated against it, not the other way around.

Common failure mode

A single large migration event scheduled for a weekend, with no realistic way to validate correctness at that scale before Monday's traffic arrives and problems become customer-visible.

4

The big-bang trap

The single decision that most reliably turns a modernization effort into a multi-year, over-budget program.

What works

Incremental migration, capability by capability or customer segment by customer segment, with value delivered and risk retired at each step, so a stalled migration still leaves something usable rather than two half-finished systems and no working whole.

What backfires

A full rewrite planned as a single release after 18 months of development, betting the entire program on one cutover event. If it fails, there's no partial progress to fall back on, just a large sunk cost and a system still running on the platform everyone agreed needed to go.

5

Sunsetting the old system

The step most migrations quietly skip, leaving the legacy system running indefinitely in a reduced but never fully retired state.

Decommissioning needs to be a scheduled, owned step with its own completion criteria, not an assumed eventual outcome once migration is "basically done." Without an explicit sunset date and owner, the old system keeps running for the small residual traffic nobody prioritized migrating, and the organization ends up maintaining two systems indefinitely instead of the one it planned for.

Checklist

Signs a modernization effort is heading for trouble

Patterns that show up consistently in migrations that stall or run significantly over budget.

  • No defined rollback criteria, or rollback has never been tested
  • The cutover plan is a single large event rather than an incremental sequence
  • Data migration validation is manual spot-checking rather than systematic reconciliation
  • No decommission date exists for the legacy system, even informally
  • The old system's remaining traffic keeps getting deprioritized in favor of new feature work on the new system
Reference only. Migration risk and appropriate pace depend heavily on system criticality, data volume, and organizational capacity; adapt accordingly.
