Legacy Modernization Execution

How a migration gets run once the decision to modernize has been made. Deciding what to modernize is the Application Portfolio Management question; this page is about the execution mechanics that determine whether the migration succeeds or stalls: choosing the seam, the strangler fig and the routing layer that makes it work, cutover and rollback, parallel-run validation, data migration sequencing, the program structure that keeps a two-year effort honest, sunsetting, and the two ways it usually goes wrong. Two worked cases, one that worked and one that was rescued.

This covers execution mechanics. See Application Portfolio Management for deciding what to modernize in the first place, Technology Diligence for assessing what's being inherited in an acquisition, and Integration & API Patterns for the anti-corruption layer and contracts a strangler migration depends on. The strangler fig pattern is Martin Fowler's (2004); the migration strategies follow the widely used "R" taxonomy (rehost, replatform, refactor, repurchase, retire, retain) that Gartner introduced and AWS extended.
Framework

Which kind of migration this is

"Modernize" covers six different projects with different risk profiles. Naming which one you are running is the first execution decision, and the one most often skipped, because a program that starts as a rehost drifts into a refactor without anyone approving the change.

StrategyWhat changesTypical durationWhere the risk sitsUse when
RehostThe infrastructure; the application is moved as-isWeeks to a few months per systemNetwork, latency, licensing, and everything that assumed the old data centerThe application is fine and the platform is the problem, or a data center lease is ending
ReplatformRuntime components (managed database, container packaging) with the code largely intactMonthsBehavioral differences in the managed service; the cutoverOperational cost and reliability are the drivers and the code is sound
Refactor or rearchitectThe code and its structure, usually toward services and a new data modelOne to three yearsEverywhere; this is where the strangler fig and everything below appliesThe application blocks the business and buying is not an option

Most of this page is about the third row, because that is the one that fails. Rehost and replatform fail on cutover mechanics, covered in section 2. Repurchase fails on data migration, covered in section 4. Retire fails on the sunset discipline in section 6, which is why estates carry so many systems that were "retired" years ago.

Framework

The strangler fig pattern, and the layer that makes it work

The dominant strategy for modernizing a live system without a high-risk, high-visibility cutover: grow the new system around the edges of the old one until the old one can be safely retired.

The mechanism

New functionality is built in the new system and routed to it, while remaining functionality continues running in the old system, with a routing layer (a proxy, an API gateway, a facade, a feature flag) directing each request to whichever system currently owns it. Over time, more capability migrates to the new system until the old system handles nothing and can be decommissioned. The old system shrinks gradually instead of being replaced in a single event, which is what makes this the lower-risk default over a full rewrite and cutover. Two supporting pieces are load-bearing: the routing layer has to exist before the first capability moves, and an anti-corruption layer translates between the old model and the new domain model so the new services never inherit the old shape.

Choosing the seam

The strangler works capability by capability, and the order matters. Start with a capability that is valuable enough to prove the approach, self-contained enough that it does not drag the whole data model with it, and low enough in blast radius that a failure is recoverable. Candidates ranked by seam quality: a read-only capability (reporting, search) first, because it can be shadowed and compared at no risk; then a capability with its own data (notifications, a document store); then transactional capabilities in order of decreasing isolation; the shared core (accounts, orders, the ledger) last. Cutting by customer segment or by traffic percentage is the alternative axis, useful when the capabilities cannot be separated but the customers can.

The first capability moved should take a quarter, produce visible value, and exercise every mechanism on this page (routing, parallel run, cutover, rollback, and a small data migration) at small scale. Programs that start with the hardest capability because it is the most valuable discover the mechanics under maximum pressure.
1

Cutover planning and rollback criteria

Every cutover, whether a full system swap or a single capability moving to the new system, needs a defined rollback trigger decided before the cutover happens rather than improvised during it.

Practice

Specific, pre-agreed rollback criteria (error rate above X percent, latency above Y, a defined list of critical functions that must work correctly) checked immediately after cutover, with the rollback mechanism tested in advance rather than assumed to work when it's needed under pressure. The cutover itself is run as an incident, with an incident commander, a timeline, and the roles from Incident Response, because it is a planned incident and the same discipline applies. The go/no-go decision has a named owner and a checklist, and the checklist includes the rollback rehearsal date.

Common failure mode

"We'll roll back if it looks bad" as the entire rollback plan, which under pressure becomes a debate about whether it's bad enough yet, while customer impact accumulates during the debate. The second failure is a rollback that was never rehearsed and turns out to require a data step nobody scripted, so the team is now writing a migration backward at 2am.

2

Parallel-run validation

Before fully trusting the new system, run it alongside the old one and compare outputs on live traffic.

Practice

Shadow traffic sent to both systems, with outputs compared automatically and discrepancies flagged, for long enough to build confidence: weeks for a low-volume system, potentially longer for something with meaningful seasonal or cyclical variation in the data it processes. The comparison needs a defined tolerance (exact match for a ledger, a rounding tolerance for a pricing engine, a semantic match for search results) and a defined exit criterion (discrepancy rate below X for Y consecutive days including a period end) agreed before the run starts. Every discrepancy is triaged into one of three buckets: new system wrong, old system wrong, or both acceptable. The second bucket is more common than anyone expects and is one of the quiet benefits of the exercise.

Common failure mode

A parallel run cut short because it's "looking fine so far," which misses the edge case that only shows up during month-end processing, a holiday traffic spike, or some other pattern the shortened window never covered. The second failure is a parallel run with no tolerance defined, so the team argues about whether a discrepancy matters instead of whether it exists, and the run never has an end condition it can meet.

Data migration sequencing

Moving the data is usually harder and riskier than moving the code, and it's where migrations most often go over budget and over timeline. The sequence below is the one that survives contact with a live system.

StepWhat happensThe check before moving on
1. BackfillHistorical data copied into the new store in batches, transformed through the anti-corruption layer, with the old system still the system of recordRow counts and checksums reconcile per batch; a sample of records compared field by field
2. Change data captureOngoing changes in the old system streamed to the new store, so the copy stays current while validation runsReplication lag measured and bounded; a reconciliation job runs nightly and reports drift
3. Dual-read validationThe new system serves reads in shadow, compared against the old, per the parallel run aboveDiscrepancy rate under the agreed tolerance across a full business cycle
4. Dual-write, old system primaryWrites go to both; the old system remains the source of truth and the new one is checked against itWrite reconciliation clean; the rollback path (stop writing to new) rehearsed
5. Cutover, new system primaryWrites go to the new system first; the old system receives them via reverse replication so it remains a valid rollback targetReverse replication verified; the rollback (flip primary back) rehearsed once in a lower environment and once for real on a low-risk segment
6. Stop reverse replicationThe old system is now stale by design. This is the point of no return and is a dated, signed decisionRollback window declared closed; the decommission clock in section 6 starts
Keep the old system's data as the system of record until the new system has been validated against it. Dual-write without a reconciliation job is the most common way a migration silently corrupts data: both stores accept writes, they diverge, and nobody notices until a customer does. The reconciliation job is the migration's most important piece of code and is usually the last one written.
4

The program structure that keeps a two-year effort honest

A refactor of a core system outlasts most executives' attention span and at least one budget cycle. The mechanics above handle risk per cutover; this handles the risk that the program itself drifts.

What works

A migration tracker with one row per capability, showing its strategy, its seam, its percentage of traffic on the new path, its cutover date, and its decommission date, reviewed monthly by the sponsor. Value delivered at each step: every capability moved either retires something, unblocks a feature, or removes a cost, and the tracker records which. A fixed cadence for the go/no-go decisions, with the same checklist each time. A named business sponsor who is not the CTO, because a migration with only an engineering sponsor gets cut in the first downturn per Technology Strategy During a Downturn. And an explicit budget line for the double-running cost, which peaks in the middle of the program and surprises every CFO who was not told about it in year one.

What backfires

A program reported as percent complete, which is a number nobody can verify and which sits at 80 percent for a year. A scope that grows because the new system is where every new feature wants to be built, so the team modernizing the old system is also the team shipping the roadmap, and the migration becomes the thing that happens when there is time. And a sponsor change: the executive who approved the program leaves, the replacement did not choose it, and the program has no artifact that shows what it has already delivered.

MeasureWhat it tells the sponsor
Share of traffic (or transactions) served by the new path, per capabilityReal progress, as opposed to percent complete; it can only be gamed by moving traffic
Capabilities decommissioned, and run cost removedWhether the old system is shrinking or the estate is growing
Double-run cost this month, against the planWhether the program is on its cost curve; this number should start falling by the midpoint
Defect and incident rate on migrated capabilities versus the old pathWhether the new system is better, and whether the parallel run was long enough
Features unblocked or delivered because of the migrationThe value story for the board, in the terms of Board Reporting
5

The big-bang trap

The single decision that most reliably turns a modernization effort into a multi-year, over-budget program.

What works

Incremental migration, capability by capability or customer segment by customer segment, with value delivered and risk retired at each step, so a stalled migration still leaves something usable rather than two half-finished systems and no working whole. The routing layer is what makes incremental possible; the tracker is what makes it visible.

What backfires

A full rewrite planned as a single release after 18 months of development, betting the entire program on one cutover event. If it fails, there's no partial progress to fall back on, only a large sunk cost and a system still running on the platform everyone agreed needed to go. The rewrite also has to reproduce every behavior of the old system, including the ones nobody documented and the ones that are bugs customers depend on, before it can ship anything, which is why the 18 months becomes 30.

6

Sunsetting the old system

The step most migrations quietly skip, leaving the legacy system running indefinitely in a reduced but never fully retired state.

Practice

Decommissioning needs to be a scheduled, owned step with its own completion criteria rather than an assumed eventual outcome once migration is "basically done." The checklist: no traffic for 30 days, confirmed from the routing layer's logs rather than assumed; every integration and scheduled job that called it identified and repointed or retired; data archived to the retention schedule the Data Governance page describes, with the legal hold check done; licenses, hosting, monitoring, and support contracts cancelled with dates; credentials and service accounts removed per Identity & Access Architecture; and the run-cost saving recorded against the program so it appears in the budget rather than in a slide.

Common failure mode

Without an explicit sunset date and owner, the old system keeps running for the small residual traffic nobody prioritized migrating, and the organization ends up maintaining two systems indefinitely instead of the one it planned for. The residual traffic is usually a nightly report, a partner integration, and one internal team's spreadsheet macro, none of which anyone will own moving, all of which cost less to move than a year of running the old system.

What it cost that the plan missed: the double-run overshoot, and a quarter of the new team's capacity spent characterizing undocumented behavior in the old tax logic.

Worked example

The rewrite that stalled, and how it was rescued

A logistics company's order management system, rewritten from scratch by a separate team, planned for 18 months, at month 26 with nothing in production.

The situation at month 26

The new system had roughly 70 percent of the old one's features by the team's own estimate, a figure that had been between 60 and 80 for a year. The old system had kept evolving, because the business could not stop for two years, so the target kept moving. No routing layer existed; the plan had always been a weekend cutover once the new system reached parity. The rewrite team and the legacy team were different people who disagreed about what parity meant. Cost to date: $4.2M. The CEO's question to the new CTO was whether to cancel it.

The rescue

Neither cancel nor continue. The CTO stopped feature work on the new system for six weeks and used the time to build the missing routing layer in front of the old one and an anti-corruption layer over its order model. Then the parity goal was abandoned: instead of finishing the rewrite, the 70 percent that existed was carved into capabilities and each one was strangled in, starting with order tracking (read-only, low risk), using the parallel-run and cutover mechanics above. The two teams were merged into one owning both paths. Six months later, 55 percent of order traffic ran on the new path, three capabilities of the old system had been decommissioned, and the program was reporting traffic share and cost removed instead of percent complete. Total cost ended at $6.1M against an original $3M plan, which is the price of the first 26 months; the last two capabilities were retired eleven months after the rescue began. The two-year rewrite with nothing in production became a strangler migration that had been running, unknowingly, all along.

The general lesson: a stalled rewrite is almost always rescuable by adding the routing layer it skipped and shipping what exists incrementally. The sunk cost is real; the question at month 26 is only whether the next dollar is better spent finishing a big bang or starting to strangle, and it is nearly always the latter.
Checklist

Signs a modernization effort is heading for trouble

Patterns that show up consistently in migrations that stall or run significantly over budget.

  • Nobody can say which of the six strategies the program is, or it has changed without a decision
  • No routing layer exists, and the plan depends on reaching parity before anything ships
  • No defined rollback criteria, or rollback has never been rehearsed
  • The cutover plan is a single large event rather than an incremental sequence
  • The parallel run has no tolerance or exit criterion, or did not span a period end
  • Data migration validation is manual spot-checking rather than a reconciliation job
  • Progress is reported as percent complete rather than as traffic on the new path and systems decommissioned
  • The only sponsor is in engineering, and the double-run cost was never put in front of the CFO
  • No decommission date exists for the legacy system, even informally
  • The old system's remaining traffic keeps getting deprioritized in favor of new feature work on the new system
